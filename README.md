# hcminer — GPU-майнер для Hashcats (Robinhood Chain)

Консольный майнер на CUDA + супервизор на Python, чтобы считать proof-of-work
Hashcats на арендованных видеокартах (например 4× RTX 5090 на Vast.ai) вместо
браузерного WebGPU-майнера.

---

## Прочитайте это до запуска

**1. Экономика почти наверняка отрицательная.** За каждого принятого кота
платится вход в ETH, и он удваивается каждую эпоху. Аренда GPU на фоне этого —
мелочь, основная статья расходов именно вход:

```
$ python3 -m hcminer.cli --config config.toml econ --hashrate 8e9 --rent 1.928 --eth-usd 3000

hashrate            8.00 GH/s
difficulty          42 zero bits  (~4.398e+12 hashes per cat)
expected time/cat   9.2 min
cats per day        157.161

rent                $1.928/h  =  $46.27/day
  rent per cat      $0.29
  entry per cat     $30.00  (0.01 ETH @ $3,000)
  TOTAL per cat     $30.29
```

Кот окупается, только если продаётся дороже, чем «TOTAL per cat». Посчитайте
`econ` на живых значениях сети **до** того, как арендовать мощности.

**2. Схема хэширования в этом репозитории не подтверждена.** У меня не было
доступа к контракту `0xCA75DF55Cc9C476DB27a7375D1fc8E794cf80721` (сеть закрыта
из среды сборки), поэтому layout в `config.example.toml` — заглушка. В проекте
есть инструменты, которые **выводят реальную схему из уже принятого минта** и
проверяют её, и `hcminer mine` не стартует, пока вы не поставите
`pow.verified = true`. Не отключайте эту проверку: майнинг по неверной схеме
сожжёт время GPU на хэши, которые контракт отвергнет.

**3. Ключ кошелька.** Приватный ключ читается только из переменной окружения и
никогда не пишется на диск. На арендованной чужой машине используйте отдельный
кошелёк с суммой на несколько минтов, а не основной.

## Что уже проверено

`./scripts/run_tests.sh` (работает без GPU):

| Проверка | Что гарантирует |
|---|---|
| keccak-ядро vs pycryptodome, 304 вектора | GPU-код считает настоящий keccak256, как в Solidity |
| вставка nonce в дорожки, все 109 выравниваний | оптимизация ядра не портит прообраз |

| восстановление схемы из синтетического минта | инструмент `solve-schema` реально находит layout |

Что **не** проверено здесь: реальные вызовы контракта и скорость на железе —
это делается на самом сервере командами `state`, `bench`, `verify`.

## Быстрый старт на Vast.ai

```bash
git clone <этот-репозиторий> && cd hsdfiuhds-3
./scripts/setup_vast.sh          # CUDA toolkit, зависимости, сборка под вашу карту, самотесты
python3 -m hcminer.cli bench --seconds 15    # реальная скорость рига
cp config.example.toml config.toml
```

RTX 5090 — это Blackwell, `sm_120`, нужен CUDA ≥ 12.8 (в образе
`vastai/base-image_cuda-13.2.1` он есть). Скрипт определяет compute capability
сам; вручную: `make -C src/cuda CUDA_ARCH=120`.

## Рабочий порядок

### 1. Разобрать контракт

```bash
python3 -m hcminer.cli discover
```

Скачивает верифицированный ABI с Blockscout, показывает функции-кандидаты на
минт, view-функции состояния (target / prev work / anchor / price) и события,
сохраняет `discover/abi.json` и последние успешные минты с раскодированными
аргументами в `discover/mints.json`.

Подставьте настоящие сигнатуры в `config.toml` → `[contract.state]`,
`[contract.mint]`.

### 2. Восстановить схему PoW

Возьмите один принятый минт: адрес майнера и nonce из транзакции, а
`prev_work`/`anchor` — из состояния контракта **в блоке перед ней**
(`hcminer state` плюс `discover/mints.json`). Запишите в `observations.json`
(шаблон — `observations.example.json`) и запустите:

```bash
python3 -m hcminer.cli solve-schema --observations observations.json --min-zero-bits 40
```

Инструмент прогоняет 261 вариант порядка полей и кодировок и оставляет те, при
которых хэш реально оказывается ниже target. Совпадение на 40+ нулевых битах
случайным быть не может, так что единственный выживший кандидат — это и есть
схема контракта. Если кандидатов несколько — добавьте второй минт в файл.

Результат впишите в `[pow] schema`.

### 3. Проверить и только потом майнить

```bash
python3 -m hcminer.cli verify --observations observations.json   # должно быть OK
# затем в config.toml:  [pow] verified = true

python3 -m hcminer.cli preflight          # конфиг, RPC, контракт, кошелёк, баланс, лимиты, GPU
python3 -m hcminer.cli mine --dry-run     # печатает готовую транзакцию, ничего не шлёт
export HC_PRIVATE_KEY=0x...               # ключ только в окружении
python3 -m hcminer.cli mine               # боевой запуск (limits.dry_run = false)
```

`preflight` — read-only: ничего не подписывает и не шлёт. Он ловит ровно те ошибки,
которые стоят денег: chain id не тот, в `contract.address` нет кода, target или
цена читаются мусором, ключ в окружении не от того кошелька, на балансе не хватает
на минт с газом, `max_spend_eth` ниже цены входа (тогда каждый минт будет
блокироваться), майнер под GPU не собран.

Цикл майнинга: читает состояние → раздаёт job на все GPU → найденное решение
пересчитывает на CPU → симулирует `eth_call` (revert ничего не стоит) →
проверяет лимиты → подписывает и отправляет транзакцию. При смене
`prev_work`/`anchor`/target job перевыпускается автоматически.

## Конфигурация

Вся специфика контракта — в `config.toml`, в коде её нет. Ключевые блоки:

- `[contract.state]` — сигнатуры view-функций; `pow.target_is_bits = true`, если
  контракт отдаёт число нулевых битов, а не 256-битный порог.
- `[contract.mint]` — сигнатура функции минта, откуда брать аргументы
  (`nonce`, `miner`, `prev_work`, `anchor`, `hash`) и чему равен `msg.value`.
- `[pow] schema` — порядок и кодировка полей внутри keccak256, например
  `["miner:addr20", "nonce:u256", "prev_work:b32", "anchor:b32"]` — это
  `abi.encodePacked`. Для `abi.encode` (слова по 32 байта) ставьте `addr32`.
- `[pow] anchor_source` — `contract` | `arbsys` (ArbSys.arbBlockHash, Orbit-сеть) |
  `block` (хэш недавнего блока).
- `[limits]` — жёсткие стопы: `dry_run`, `max_mints`, `max_spend_eth`,
  `max_gas_price_gwei`. Майнер останавливается, а не «пробует ещё раз».

## Как устроено

```
src/keccak/keccak_core.cuh   keccak-f1600; компилируется и под CUDA, и под CPU —
                             поэтому GPU и проверка на CPU не могут разойтись
src/cuda/miner.cu            ядро + хост: многокарточный перебор nonce,
                             JSON-протокол построчно через stdin/stdout
hcminer/schema.py            layout прообраза (DSL "источник:кодировка")
hcminer/discover.py          ABI с эксплорера + восстановление схемы из минта
hcminer/chain.py             чтение target / prev_work / anchor / price
hcminer/tx.py                сборка, симуляция, подпись, лимиты трат
hcminer/economics.py         аренда против стоимости входа
hcminer/preflight.py         сквозная проверка перед первым боевым минтом
hcminer/cli.py               state | discover | solve-schema | verify | preflight |
                             bench | econ | mine
tests/                       всё, что проверяется без видеокарты
```

Прообраз GPU не зашит в ядро: супервизор присылает готовый шаблон байтов и
смещение 8 байт, которые перебирает карта. Поэтому смена схемы — это правка
конфига, а не переписывание CUDA.

Ядро считает keccak256 за один блок (прообраз до 135 байт; адрес + nonce +
prev_work + anchor = 116, помещается), состояние целиком в регистрах: ptxas
показывает 0 байт локальной памяти и 0 спиллов, 74 регистра.

## Ограничения

- Один блок keccak: прообраз длиннее 135 байт не поддерживается (схема с таким
  прообразом будет отвергнута с понятной ошибкой).
- Разбор ABI и calldata — только статические типы (uint/int/address/bytes32/bool).
- Схема с нонсом, разорванным на несколько кусков прообраза, не поддерживается.
- Пула нет: решение привязано к адресу майнера и отправляется вашим ключом.
- Сборка под `sm_120` проверялась только на целевой машине с CUDA 13.x; в этой
  среде код собирался под `sm_89` (арх-специфичных инструкций в ядре нет).
